# Locales

`ops/I18N.md` is the reference — the directory layout, the checker's full
inventory, pluralization, adding a language. This is what binds when you touch a
locale.

## Author all fifteen — but derive them, and route them through the packet

⚠️ **Reversed by the owner on 2026-09-07.** This page said "Author English. Never
any other locale, German included", on the premise that a human translator
held the other fourteen. It no longer does. An English placeholder that nobody
will translate is not the safe option; it ships English in fourteen languages.

So write all fifteen — and **derive them**. Take the verb, the noun and the
register from strings already shipped in that locale rather than composing from
scratch: `common.close_dialog` took its verb from `common.close_menu`,
`settings.github.show_token` its noun from `settings.github.personal_token`, so
the eye button and the field it labels use one word in every language.
`ai.import_max_size` took each locale's own unit — `Mo`, `МБ`.

⚠️ **The old rule's reasoning still describes a real risk; it is accepted, not
solved.** A plausible wrong value in a language nobody here reads will never be
re-examined. `scripts/i18n/check-scripts.cjs` catches a wrong writing system and
**nothing** catches wrong meaning.

⚠️ **The escape hatch is per-locale, and it does not reach `main`.** Leaving
English is defensible in the one or two locales a string genuinely defeats you
in — idiom, legal register, a claim that could widen. It is not defensible in all
fourteen, and it is not even mergeable: `tests/i18n/untranslated.test.cjs` fires
when a key holds the same value across every non-English locale, and CI
runs it. So an all-fourteen placeholder is an **owner escalation**, not a merge —
and never an `untranslated-allowlist.cjs` entry, which is for a name or URL that
genuinely is the English word.

⚠️ **Which words stay English is not a judgement call** — `ops/I18N_TERMINOLOGY.md`
decides it, in four classes, and flags the one case the shipped values do not
settle. Where that page is silent, say so and ask; a coined term is far harder to
retract than a blocked review.

Adding a key still means `npm run i18n:sync` first, then clearing
`FIELDS_TO_SYNC` to `[]`. That seeds all fifteen; the packet is where the
fourteen get their real values.

**A non-English value you wrote is reviewed by `i18n-auditor`**, never by you —
the same independence every other surface here has.

⚠️ The statutory withdrawal text (`legal.withdrawal.*`) is the one place a
second locale is authored by hand, because model wording is prescribed rather
than translated. That is a transcription, not a translation. The rest of
`legal.ts` goes through the packet.

## Changing an existing English value is the silent one

`i18n:check` passes, the generator reports nothing to translate, and all fourteen
locales quietly keep saying the previous sentence — because a filled cell reads
as translated regardless of what it is a translation _of_.

So editing shipped English is never an in-place edit. Drop the key from the
other locales first (`node scripts/remove-keys.cjs`), leaving the generator
nothing to recover, then re-add the new English. `/retranslate-key` walks it.

## Translations move as files, never as chat text

⚠️ **Unchanged by the 2026-09-07 reversal above, and the reason it stays safe.**
Who authors a value moved; how it travels did not. Write into the packet files
and let `i18n:handoff:import` read them — never edit a locale file by hand, and
never carry a value through a chat message.

This is not tooling preference. **Every failure this repo has recorded came from
text passing through a message:** CJK files use curly `“…”` that a chat window
straightens, `\n` pasted literally becomes a real line break, and thirteen
wrong-script strings once shipped because a reader who does not know the language
sees plausible text. The importer validates `translation` values _out of the
packet_ — a value that never entered the packet was never validated.

## Never `rm -rf` the packet; regenerate in place

Recovery is `storedValue === entry.source ? '' : storedValue`, which cannot tell
an untranslated placeholder from a translation that is **correctly** the same
word as the English. Deleting the packet on 2026-07-23 reopened 26 such cells —
`Design`, `Menu`, `Layout`, `Pass`, `Preview`. Nothing was lost, but the
translator had to retype them.

A row that is the English in **all fourteen** locales — a name, a URL — goes in
`VERBATIM` in `handoff-catalog.cjs`: the generator pre-fills it and the
importer rejects any other value. Equal in only some locales (a cognate, a date
pattern) is not verbatim, and stays blank in a fresh packet; refill those from
their own `source` before handing over.

## Edit values through the AST

`updateModuleSource` from `scripts/i18n/locale-ast.cjs`, never text substitution.
It resolves numeric segments (`terms.sections.2`) and hyphenated ones, and quotes
correctly. A regex cannot see a quoted key: `/\b4:\s*\{/` never matches `'4': {`,
which is how an earlier implementation injected a duplicate `4: {}` into all
fifteen locales.

## Deleting a key: four reference sites, only two greppable

Before deleting anything:

1. Grep the **full dotted key and its leaf** across `src/`, `tests/`, `netlify/`
   **and `scripts/`** — that last one is what catches the handoff catalog, whose
   rows store module and path as _separate array elements_, so the dotted key
   exists nowhere as a string.
2. Confirm it is not under a registered dynamic prefix. Generate that list with
   `dynamicPrefixCallSites()` from `scripts/i18n/translator-calls.cjs`; do not
   read it from prose, where it drifts.
3. Delete with `node scripts/remove-keys.cjs <module.key>…`, never by hand.
4. Run `npm run i18n:check` **and** `npm test` — `test:i18n` is the runner that
   catches a stale catalog row; `npx vitest run` alone does not.

⚠️ Verify with a real loop. A 2026-08-29 sweep of 25 keys used
`for k in $KEYS` over a space-joined string; **zsh does not word-split unquoted
parameters**, so it ran once against the concatenation and reported all 25 clean.
Three were live. Use `while IFS= read -r`, or a real array.

## A key the packet must translate needs a catalog row

The handoff packet carries **only catalogued keys**. A new user-facing string
with no row in `scripts/i18n/handoff-catalog.cjs` is generated, synced, shipped
as English in fourteen locales, and never appears in a packet — silently, since
every check passes.

Put the reasoning a translator needs into the row's `context`: what the string
must not claim, what surrounds it in the UI, which tokens are product names.

## Baseline entries mean opposite things

- `bare-literal-baseline.js` — an entry is a **decision**, and carries a `reason`
  saying why routing through `src/locales/` would be wrong. The default is to
  route it.
- `script-contamination-baseline.cjs` — an entry is a **bug**. Broken text is
  never defensible; fix the string. It ships empty and should stay empty.

Both fail on a stale entry as well as a new finding, so neither can outlive what
it covers.

## Voice

Third person: **KiwiCV** is the subject, or the user is. Never "we", "our", "us".
Address the user directly. No corporate register — this is an everyday tool, not
a business suite. Keep CV advice expert but plainly worded.

⚠️ This is the rule most often missed, because until 2026-09 it lived only inside
a long page about translation mechanics, which nobody opens while writing English
copy. It applies to changelog entries, modal copy and marketing alike — anywhere
a user reads a sentence.

`pt` is **European Portuguese, informal _tu_** (owner, 2026-10-05): _secção_,
_eliminar_, _Tens a certeza?_. Brazilian forms the locale still carries until the
consistency pass — `Excluir`, `seção`, `Tem certeza`, _você_/_seu_/_sua_ — are not
siblings to derive from.

**Legal text (`legal.ts`) is formal** (owner, 2026-10-08): _vous_, _usted_,
_Lei_, _u_, _Państwo_, _вы_, _ви_, _вие_, _siz_, pt-PT formal; ja as in the UI. **German and Swedish are the exceptions and keep _du_** (German
matches the product voice; Swedish legal and consumer text uses _du_, _ni_ reads
stiff). Polish uses _Państwo_ (as the withdrawal text already does), Italian
_Lei_, pt-PT third-person formal (_Pode … a sua_, _o utilizador_), zh _您_
throughout (the zh product UI is _你_, owner 2026-10-12, matching every locale that distinguishes register except ja, which keeps its polite form), except `legal.contact.message`, which uses _你_ (owner 2026-10-12): it reads as a product contact card. The legal-update consent modal (`legal.update`) follows the
documents. One AI term per locale: tr _Yapay Zeka_, bg _ИИ_, it _IA_;
_Vertex AI_ stays as a product name.
The UI register rule above does not apply to `legal.ts`; derive legal wording
from formal legal siblings, not from UI strings.
